## Findings

### F-01 — medium — `PrepSourceStatus` has no representation for AC-0007's "skipped" outcome
AC-0007 (`plan.dd.md`) requires: *"every run reports per-source outcome (unchanged, appended, replaced, new, **skipped**, unreadable, unsupported)."* The frozen v2 contract's `Outcomes` clause (architecture.contracts) defines `PrepSourceStatus = New | Unchanged | Appended | Replaced{reason} | Unreadable | Unsupported | Missing` — seven variants, but the seventh is `Missing`, not `Skipped`, and nothing in the contract states these are the same concept. Discovery-time exclusions (symlinks, hidden entries) are already covered separately by `PrepSkipCounts`/`PrepDiscovery` — that's a different axis (never becomes a `PrepSourceStat` at all) from a per-source *outcome* on an already-discovered source. If the AC's "skipped" means something else (e.g., a source present but excluded by `--harness` filter or an unbound-harness root), there's no status variant for it today; `Unsupported` is the closest but is described elsewhere as "harness has no binding," not "operator excluded it." Concretely: does a `--harness claude-code` run that discovers an OMP source report that OMP source as `Unsupported` (already the case per the SDK contract: *"a root whose harness has no binding is reported supported = false with its sources Unsupported"*) even though the harness filter, not binding absence, is why it's excluded? If so the vocabularies genuinely coincide and this is a naming inconsistency only; if not, a status is missing. Either way this should be resolved in the guide text, not left to tk-0003's judgement, since `PrepSourceStatus` is sealed with `core::prep` in wave 0 and unavailable to wave-1 units afterward.
**Disposition needed:** PM confirms `Missing == skipped` mapping (and fixes the plan/guide wording) or adds an explicit status before seal.

### F-02 — medium — row-schema optionality is unstated for fields phase-2 lanes require to be null
The frozen `Rows` contract clause lists `calls: … ts, ts_ms, model, …, input, cw_1h, cw_5m, cache_read, output …` and `turns: … started_ts, started_ts_ms …` without marking any of these `Option<>` (contrast with fields the same clause *does* explicitly flag, e.g. `stop_reason (last non-null)`, `cache_write_basis (…| none)`). The POC's current `PrepCallRow` (`crates/core/src/prep.rs:57-77`) makes this concrete: `ts: String` and `ts_ms: i64` are non-optional today. But the guide's own planned phase-2 lanes explicitly require untimed, usage-less rows against this same table: Cursor transcript folds *"carry no ids, timestamps, models or usage: rows keyed by native offset with explicit nulls"*; VS Code Copilot and Codex likewise note the native/query mapping "omits usage." A `calls` row with no timestamp cannot satisfy a non-optional `ts: String` field. Similarly, the row-prefix fields `native_offset, native_key` (shared by every table) aren't marked optional at the row level even though the separate `NativeAddress` DTO used for `record_at` fetches *is* `{offset: Option<u64>, key: Option<String>}` — for Snapshot-kind sources (Cursor IDE, VS Code Copilot journal) a row addressed only by `native_key` needs `native_offset` absent, which the frozen prose doesn't say.
This matters specifically because of the guide's own constraint: *"no wave-1 unit may change core::prep… a needed change is a PM contract delta"* and *"no phase-2 port change is planned; any required change is a PM contract delta sealed before phase-2 dispatch."* If tk-0001 seals `ts`/`ts_ms`/`native_offset` as non-optional (as the POC currently has them), phase 2 hits exactly the contract delta the guide says it's trying to avoid, on a baseline the guide describes as final for these fields.
**Disposition needed:** PM adds explicit `Option<>` annotations to the frozen row schema for every field a stated phase-2 lane needs to omit, before `harness builder contracts --seal`.

### F-03 — low — `cp-000b`'s proof list omits `vd-0006`, which is the check that actually proves the read-only-loader claim
AC-000b requires "native stores are opened read-only and never locked, renamed or written." The capability `cp-000b` (owner tk-0006) lists proof `[vd-0002, vd-0003, vd-0005, vd-0008]`. `vd-0006`'s own description is *"JSONL prep loader on real temp files: … read-only opens, anchors …"* — the concrete assertion for this half of the claim — but it isn't in `cp-000b`'s proof array, and `tk-0003` (the loader's owning unit) isn't listed as an owner or contributor to `cp-000b` either. The check exists and is required by `tk-0003`'s own responsibility text, so this is a traceability gap in the capability→check map, not a missing proof.
**Disposition needed:** cosmetic; add `vd-0006` to `cp-000b`'s proof list at next guide revision (does not block seal).

## Answers to "what to assess"

1. **Lane independence:** genuine. All four wave-1 units (`tk-0002` Claude fold, `tk-0003` engine+loader, `tk-0004` store, `tk-0005` CLI) declare `reads` limited to `tk-0001`'s frozen files only — zero cross-reads among wave-1 units, verified in the JSON. The state protocol that would otherwise couple engine↔store is resolved by freezing `PrepState`/`PrepSourceState`/the commit-order contract in the wave-0 baseline; engine and store integrate only through those sealed types, never through each other's code. One coupling the guide itself corrects versus the POC: `output-prep`'s current `project_of`/`agent_of` helpers parse Claude-specific path conventions (`-Users-<name>-rest`) directly in the store (`crates/output-prep/src/lib.rs:198-210`); the v2 contract moves this to `PrepSourceMeta{is_sub, agent_id, project}` supplied by each fold's `describe()`, correctly removing a real Claude-knowledge leak from the harness-agnostic store. No hidden coupling found beyond F-01/F-02 (contract precision, not lane coupling).

2. **v2 contract completeness:** mostly complete and correct — `SessionFacts` was checked directly against Plan 029's stated needs (`session-status-prime-answers.md`) and matches: `latest_context` = latest dedup main-chain call's `input+cache_read+cache_write` (Plan 029 answer §3), `compactions: Option<CompactionCounts>` = None only absent native markers with manual/auto split (Plan 029 answer §4), `last_event_ts` = latest native event timestamp never mtime (Plan 029 answer, "last updated" ruling). No Parquet/SQLite/engine leakage into core/sdk in the contract text, and `arch-check` (vd-0009) enforces it mechanically — I confirmed the allowlist source only lists `serde`/`serde_json`/`sha2`/`time`/`regex`/`globset` for core/sdk. Gaps found: F-01 (status vocabulary), F-02 (row nullability).

3. **AC→entrypoint→owner→check:** every phase-1 capability (`cp-0001`…`cp-0005`, `cp-0007`, `cp-0008`, `cp-000a`, `cp-000b`, `cp-000d`) has exactly one named owning unit and a concrete `vd-XXXX` check with a real command/args/cwd/timeout — I read all 16 checks and none are placeholders. AC-0004 parity: `vd-000a` is a field-by-field diff against a copied reference parser with numbers-only output, and the guide's `review.when` clause explicitly states *"AC-0004 divergences are accepted or rejected by the reviewer"* — this is genuinely exact-or-explained, not rounded, and the risk register (`rk-0001`) names the two known edge cases (window-boundary state, 0.1s gap-rounding ties) instead of hiding them.

4. **Phase-2 deferral:** sound in structure (guide v2 re-seals on the phase-1 composed SHA, per-lane pattern/kind/checkpoint semantics are already specified in architecture.contracts for every planned phase-2 fold, not invented later) but the deferral's soundness is exactly what F-02 threatens — the phase-2 lane descriptions assume nullable fields the frozen v1 row schema doesn't grant. Fix F-02 and this answer becomes an unqualified yes.

5. **Privacy/safety/crash/compaction proofs:** adequate. Crash atomicity (AC-0001): I read the POC's actual `commit()` (`output-prep/src/lib.rs:277-367`) and confirmed the ordering the contract requires already exists in the POC — parts written+fsynced, then sources/sessions snapshots+fsynced, then `state.json` via temp-file+fsync+atomic rename+directory fsync — tk-0004 only needs to add the exclusive advisory lock and `compact()`, not invent the durability pattern from scratch, which makes `vd-0004`'s scope realistic. Live-file safety (AC-0002): tier EXTEND is honest — the POC's `live_proof.py` already ran 22 randomized runs with 0 failures (real measured evidence, not aspirational), phase 1 just ports it to the v2 schema and wires it into a lane. Compaction (AC-0008): POC never compacts today (verified: no `compact()` method in the trait or impl I read), so `tier BUILD` is correctly not overclaimed as "extend." Privacy (AC-000b): content gating is structurally sound (`PrepOptions.include_content`, `record()` "refused before any native read"), only the F-03 traceability gap.

6. **Backpressure honesty:** the survey's certainty is `Partial` and I found that honest, not hedged — every `EXTEND` tier row cites specific prior POC measurement (e.g., 55,607 calls matched, 22/22 live runs, 3.46s cold) rather than assuming success, every `BUILD` tier row states plainly that no prior test exists, and I spot-checked three probes (arch-check scan scope, proof-mode list, catalogue assertion) directly against source and all three were accurate to the line numbers cited. `rk-0007` (no DuckDB installed) correctly gates only the phase-2 recipe capability, not phase 1.
